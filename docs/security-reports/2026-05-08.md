### 🟠 WARNING

**WARN-1: Price tracker photo upload lacks magic-byte validation**

- **File:** `winebox/routers/price_tracker.py` (line 206)
- **Detail:** The price tracker photo upload validates `content_type` (line 192) and file size, but does not perform magic-byte validation like `ImageStorageService.save_image()` does for wine label images. The file extension is extracted from the user-supplied filename (`photo.filename.rsplit(".", 1)[-1].lower()`) and used directly in the saved filename. Since `content_type` is a client-declared header and trivially spoofable, a user could upload a file with a `.html` or `.svg` extension containing XSS payloads. The file would be saved and later served by `FileResponse` (line 412) with a content type inferred from that extension.
- **Contrast:** `ImageStorageService.save_image()` (line 155-165) correctly detects the real image type from magic bytes and uses the detected extension — the price tracker should follow the same pattern.
- **Recommendation:** Add magic-byte validation to the price tracker photo upload (reuse `detect_image_type()` from `image_storage.py`) and use the detected extension instead of the user-declared one. Alternatively, refactor to use `ImageStorageService` directly.

**WARN-2: Price photo deletion missing path traversal guard**

- **File:** `winebox/routers/price_tracker.py` (lines 311-314)
- **Detail:** When deleting a photo on price entry removal, the code does `_photo_storage_path() / entry.photo_path` then `unlink()` without any path traversal check. The value comes from the database (set at upload time from `uuid.hex + ext`), so exploitation requires database poisoning. However, the `get_price_photo` endpoint (line 393) correctly checks for traversal (`"/" in filename or "\\" in filename or ".." in filename`), showing awareness of the risk but inconsistent application.
- **Recommendation:** Add the same traversal check before `unlink()`, or better, use `ImageStorageService._safe_resolve()` pattern (`resolve()` + `relative_to()` check).

**WARN-3: Reference data endpoints have no rate limiting**

- **File:** `winebox/routers/reference.py`
- **Detail:** All reference data endpoints (`/api/reference/wine-types`, `/api/reference/grapes`, `/api/reference/regions`, `/api/reference/classifications`) have no rate limiting at all. While they serve read-only public data, they execute database queries on every request. Without rate limits, they could be abused for scraping or used in a DoS attack to exhaust MongoDB connections.
- **Recommendation:** Add rate limiting (e.g., `120/minute`) to reference data endpoints, consistent with the xwines search endpoint.

**WARN-4: Admin `delete_user` does not clean up CellarItem or CellarEvent documents**

- **File:** `winebox/admin/routers/admin.py` (lines 303-330)
- **Detail:** When an admin deletes a user, wines, transactions, import batches, and raw uploads are cleaned up, but `CellarItem` (the `cellars` collection) and `CellarEvent` (the `cellar_events` collection) are NOT deleted. This leaves orphaned physical inventory and event history in the database after user deletion. Additionally, the `RawUploadRow` deletion (line 317) queries `{"owner_id": user.id}` but `RawUploadRow` has no `owner_id` field — it only has `batch_id`. This query silently deletes nothing.
- **Recommendation:** Add CellarItem and CellarEvent deletion. Fix RawUploadRow deletion to query by `batch_id` from the user's batches.

### 🟡 INFO (Best practice recommendations)

**INFO-1: E2E test secret keys hardcoded in tasks.py**

- **File:** `tasks.py` (lines 283, 2017)
- **Values:** `"e2e-test-secret-key-not-for-production-use-1234567890"` and `"oat-e2e-test-secret-key-1234567890"`
- **Detail:** Clearly labelled test-only values used for isolated E2E test environments. Not used in production. Low risk. Carried forward from previous review (2026-04-26, INFO-5).
- **Recommendation:** Consider loading from an environment variable for consistency with project conventions.

**INFO-2: Defence-in-depth: `delete_wine` CellarEvent/Transaction queries lack `owner_id`**

- **File:** `winebox/routers/wines/crud.py` (lines 188-189)
- **Detail:** `CellarEvent.find({"wine_id": wine.id}).delete()` and `Transaction.find({"wine_id": wine.id}).delete()` filter only by `wine_id` without `owner_id`/`cellar_id`. The wine itself is fetched with owner verification via `get_wine_or_404`, so `wine.id` is an ObjectId guaranteed to belong to the user. Not exploitable in practice (ObjectIds are unique), but violates the stated data isolation principle.
- **Recommendation:** Add `"owner_id": current_user.id` or `"cellar_id": current_user.id` to the deletion queries for defence-in-depth.

**INFO-3: Defence-in-depth: Wine batch lookups in export/event views lack `owner_id`**

- **Files:** `winebox/routers/export.py` (line 250), `winebox/services/cellar_event_view.py` (line 179)
- **Detail:** `Wine.find({"_id": {"$in": wine_oids}})` lookups omit `owner_id`. The `wine_oids` come from owner-scoped event queries, so in normal operation only the user's wines are returned. A corrupted `wine_id` in an event document could theoretically leak another user's wine details into an export.
- **Recommendation:** Add `"owner_id": owner_id` to these Wine batch lookups.

**INFO-4: Unbounded `to_list()` calls on per-item event queries**

- **Files:** `winebox/routers/bottles.py` (line 190), `winebox/services/cellar_event_view.py` (line 242)
- **Detail:** Several queries call `.to_list()` without a `length` parameter, which could theoretically load unbounded results. These are bounded by practical usage (a single bottle won't have millions of events), but should have a safety cap.
- **Recommendation:** Add `length=MAX_USER_RESULTSET` to these calls.

#### 2. Hardcoded Secrets Scan

#### 3. Authentication & Authorization Audit

- **All endpoints** handling user data require `RequireAuth` or `RequireAdmin`.
- **All primary database queries** for user-owned data filter by `owner_id` or `cellar_id`.
- Public endpoints (`/api/reference/*`, `/api/xwines/*`, `/health`, `/api/config/analytics`) serve only static reference data — no user information exposed.
- Admin endpoints use `RequireAdmin` (not just `RequireAuth`) — verified in both main app and admin panel.
- Admin panel has IP allowlist at nginx layer + application-level `RequireAdmin`.
- Admin panel defaults to OAT database — production requires FQDN check.
- Password changes invalidate all existing tokens via dual mechanism:
  - Per-token blacklist (JTI-based)
  - Bulk `tokens_invalidated_after` cutoff on user document
- Password reset also invalidates all tokens (`on_after_reset_password`).
- User registration validates email format (Pydantic `EmailStr`) and password length (8+ chars).
- Constant-time password comparison via Argon2 `verify()` with dummy hash for non-existent users.

#### 4. NoSQL Injection & Query Safety

- All regex searches use `re.escape()` before compilation (verified across all routers and services).
- No unsafe MongoDB operators (`$where`, `$expr`, `$accumulator`, `$function`) found.
- All `ObjectId` parsing wrapped in `try/except InvalidId` with proper 400/404 responses.
- All API inputs validated via Pydantic models — no raw `dict` or untyped JSON bodies.
- Search query length capped at 200 characters.
- `$in` arrays always derived from server-side queries, never directly from user input.

#### 5. Input Validation & Injection Prevention

- Wine label image uploads validated: magic byte detection, extension whitelist, size limits (default 10 MB).
- Path traversal prevented in image serving (`_safe_resolve()` rejects `..`, `/`, `\` components).
- Generated filenames use UUIDs, not user input.
- Jinja2 templates use autoescaping — no `|safe` or `{% autoescape false %}` usage.
- No `eval()`, `exec()`, `__import__()`, or `compile()` in application code.
- All paginated endpoints enforce maximum limits via `Query(ge=1, le=MAX_PAGE_SIZE)` (MAX_PAGE_SIZE=200).
- Hard ceilings: `MAX_USER_RESULTSET=10,000`, `MAX_REFERENCE_RESULTSET=5,000`.

#### 6. Rate Limiting & DoS Prevention

- **Global:** 60 requests/minute per IP.
- **Login:** 30/minute, 200/hour + account lockout after 5 failed attempts (15-minute window).
- **Admin login:** 5/minute (stricter).
- **Registration:** 10/minute, 50/hour.
- **Password reset/change:** 5/minute, 20/hour.
- **Search:** 120/minute, 2000/hour with 200-char query limit.
- **Export:** 10/minute, 30/hour.
- All paginated queries bounded by `MAX_USER_RESULTSET`.
- Database query timeouts: `serverSelectionTimeoutMS=5000`, `connectTimeoutMS=10000`, `socketTimeoutMS=30000`.

#### 7. Session & Token Security

- JWT tokens use HS256 with minimum 32-character secret key (enforced at startup, blocks production start).
- Tokens include `jti` (UUID), `iat`, `exp`, and `sub` claims.
- Token lifetime: 2 hours (`ACCESS_TOKEN_EXPIRE_MINUTES=120`).
- Dual-layer revocation: per-token blacklist + bulk user invalidation cutoff.
- Revoked token cleanup runs hourly via background task.
- Purpose-specific secret derivation (SHA256) for reset/verification tokens prevents type confusion.
- Verification token lifetime: 72 hours. Reset token lifetime: 24 hours.
- No token values logged anywhere in the codebase.
- HSTS enabled in production: `max-age=31536000; includeSubDomains; preload`.

#### 8. Security Headers

- `X-Content-Type-Options: nosniff` — both FastAPI middleware and nginx static locations.
- `X-Frame-Options: DENY` — both layers.
- `X-XSS-Protection: 1; mode=block`
- `Referrer-Policy: strict-origin-when-cross-origin`
- `X-Permitted-Cross-Domain-Policies: none`
- `Permissions-Policy` restricting camera, geolocation, microphone, etc.
- `Content-Security-Policy`: `script-src 'self'` (no unsafe-inline for scripts), PostHog domains whitelisted.
- CORS: empty origin list by default (same-origin only), explicit whitelist when configured.
- Nginx: `server_tokens off`, TLS 1.2/1.3 only, strong ciphers, session tickets disabled.
- Previous INFO-2 from 2026-04-26 (nginx static headers) has been fixed.

#### 9. Data Exposure

- No stack traces, database names, or file paths in error responses.
- PostHog public API key properly separated — loaded from `/api/config/analytics` endpoint, not hardcoded in static JS.
- Image serving requires auth + ownership check — uniform 404 prevents filename enumeration.
