### Unbounded `limit` Parameters

Several list endpoints accept a `limit` query parameter with no upper bound:
- `GET /api/wines` (`limit: int = 100`, no `le=` constraint)
- `GET /api/cellar` (`limit: int = 100`, no `le=` constraint)
- `GET /api/met` (`limit: int = 100`, no `le=` constraint)
- `GET /api/transactions` (`limit: int = 100`, no `le=` constraint)
- `GET /api/search` (`limit: int = 100`, no `le=` constraint)

A client could pass `limit=1000000` to force large result sets. The default of 100 mitigates casual abuse, but explicit caps would be more robust.

## Summary

### WARNING (Address within 1 week)

1. **Password change does not invalidate all sessions** (`winebox/routers/auth.py:170-178`). When a user changes their password, only the current session's token is revoked. Other active sessions remain valid. If a user's credentials are compromised and they change their password, the attacker's existing sessions continue to work until the tokens expire (up to 2 hours). Recommendation: revoke all tokens for the user on password change, not just the current one.

2. **`python-jose` is unmaintained.** The upstream `python-jose` package has not had an official release since 2021. While the installed version (3.5.0, a community fork) patches CVE-2024-33663, the lack of active maintenance is a long-term risk. Recommendation: migrate to `PyJWT` which is actively maintained and widely used.

### INFO (Best practice recommendations)

3. **Unbounded `limit` query parameters** on 5 list endpoints (`/api/wines`, `/api/cellar`, `/api/met`, `/api/transactions`, `/api/search`). Add `le=1000` or similar upper bound via `Query(default=100, ge=1, le=1000)` to prevent clients from requesting excessively large result sets.

4. **`.gitignore` does not explicitly list `secrets.env`.** While `secrets.env` is currently loaded from a path outside the repo, adding it to `.gitignore` would provide defence-in-depth against accidental commits.

5. **X-Wines search and export endpoints lack dedicated rate limits.** These are public endpoints that can trigger expensive database queries. Consider adding per-IP rate limits (e.g., 30/minute for search, 10/minute for export).

### CLEAN (Passed review)

- **Hardcoded secrets scan** -- No secrets found in codebase
- **Authentication coverage** -- All user-data endpoints require authentication
- **Owner isolation** -- All database queries filter by `owner_id`
- **NoSQL injection protection** -- `re.escape()` used consistently, ObjectId parsing safe
- **Input validation** -- Pydantic models with appropriate constraints throughout
- **Security headers** -- Comprehensive headers including CSP, HSTS, X-Frame-Options
- **CORS configuration** -- Restricted to explicit origins
- **Token security** -- JTI-based revocation, 2-hour expiry, blacklist with cleanup
- **Password hashing** -- Argon2 with constant-time comparison
- **Account lockout** -- Protection against brute-force attacks
- **Production safety** -- Database safety check, secret key validation, debug mode enforcement
- **Git history** -- No secrets or suspicious changes in recent commits
- **Dependency vulnerabilities** -- All known CVEs are mitigated by current version pins (Pillow CVE-2026-25990, cryptography CVE-2026-26007, python-jose CVE-2024-33663, python-multipart CVE-2026-24486)
