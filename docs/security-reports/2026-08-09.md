**INFO-8: Starlette 0.50.0 is affected by CVE-2026-48710 (BadHost) — no practical impact on WineBox**

- **File:** `uv.lock` — starlette pinned at 0.50.0; patch is in starlette 1.0.1
- **CVE:** CVE-2026-48710 — Starlette reconstructs `request.url` from the HTTP Host header without validation. A malformed Host header can cause `request.url.path` to differ from the path the ASGI server actually routed, allowing middleware that makes security decisions based on `request.url.path` to be bypassed.
- **Impact on WineBox: None.** WineBox does not use path-based auth middleware. Authentication is enforced via FastAPI dependency injection (`RequireAuth`, `RequireAdmin`) on individual route handlers, which operate on the ASGI scope path (the correctly-routed path), not `request.url.path`. Additionally, nginx normalises Host headers in production.
- **Upgrade path:** FastAPI 0.128.1 constrains starlette to `<0.51.0,>=0.40.0`. Upgrading to starlette >=1.0.1 requires upgrading FastAPI to >=0.136.0. See also INFO-35 for additional Starlette CVEs.
- **Recommendation:** Plan a coordinated FastAPI + Starlette upgrade in a future maintenance cycle.
- **Status:** Carried forward from 2026-05-27 review.

**INFO-9: Cascading delete in `delete_wine` does not scope by `owner_id`**

- **File:** `winebox/routers/wines/crud.py:188-189`
- **Detail:** When deleting a wine, the cascading deletion of `CellarEvent` and `Transaction` documents filters by `wine_id` but not by `owner_id`/`cellar_id`. The wine itself is already confirmed as owned by the current user via `get_wine_or_404` (line 177), and MongoDB ObjectIds are globally unique, so there is zero practical risk. However, adding `owner_id` to the cascade filter would be a defence-in-depth improvement.
- **Impact:** None — the ownership check on the wine itself prevents any cross-user deletion.
- **Status:** Carried forward from 2026-05-28 review.

**INFO-10: Admin `delete_user` does not clean up `CellarEvent` or `CellarItem` documents**

- **File:** `winebox/admin/routers/admin.py:303-330`
- **Detail:** The admin delete-user endpoint removes wines, transactions, import batches, and raw uploads, but does not remove `CellarEvent` or `CellarItem` documents for the deleted user. This leaves orphaned data in the database. Additionally, the `RawUploadRow` cleanup queries by `owner_id` but `RawUploadRow` uses `batch_id`, so the query matches zero documents — see INFO-43 for details. No security risk — the orphaned documents are scoped by `cellar_id`/`owner_id` and cannot be accessed by other users.
- **Recommendation:** Add `CellarEvent` and `CellarItem` cleanup to the delete cascade. Fix the `RawUploadRow` query.
- **Status:** Carried forward from 2026-05-28 review.

**INFO-13: Admin deactivation does not bump `tokens_invalidated_after`**

- **File:** `winebox/admin/routers/admin.py:265-272`
- **Detail:** When an admin deactivates a user, `is_active` is set to `False` but `tokens_invalidated_after` is not bumped. Regstack's `current_user()` dependency checks `user.is_active` on every request, so the deactivated user's JWT is rejected at next use. The theoretical window between deactivation and next JWT validation (up to the request timeout) is negligible.
- **Recommendation:** Consider setting `tokens_invalidated_after = now` alongside `is_active = False` for defence-in-depth.
- **Status:** Carried forward from 2026-05-28 review.

- **File:** `winebox/routers/export.py:147`
- **Detail:** The JSON/YAML export includes `_id` and `owner_id` before they are stripped with `.pop()`. The explicit stripping works correctly. CSV export uses a different code path that selects specific fields.

- **Detail:** Content-Disposition header parameter smuggling allows filename spoofing. WineBox's image upload validation uses magic byte detection (not filename), which mitigates this vulnerability. The practical impact is low.

**INFO-50: Synchronous Anthropic client used in async functions blocks the event loop**

- **Detail:** These services use the synchronous `anthropic.Anthropic()` client inside async endpoint handlers. This blocks the event loop during API calls (60–120 second timeout). **INFO-51: cryptography 46.0.7 is affected by CVE-2026-69248 + CVE-2026-69249 — no practical impact on WineBox**

- **Detail:** CVE-2026-69248 (PKCS#12 decryption with incorrect password triggers use-after-free) and CVE-2026-69249 (CMS/SMIME signature verification memory leak). WineBox does not use PKCS#12 decryption or CMS/SMIME verification. No practical impact.
- **Upgrade path:** Requires cryptography >= 49.0.0. See INFO-7 and INFO-33.
- **Status:** Carried forward from 2026-08-04 review.

**INFO-52: CellarEvent creation in cases.py and bottles.py omits `owner_id` and `wine_id`**

- **Files:** `winebox/routers/cases.py:276-287`, `winebox/routers/bottles.py:144-157`
- **Detail:** When creating CellarEvent records via the case/bottle event endpoints, `owner_id` and `wine_id` fields are not populated. The canonical creation path in `bottle_service.py` always sets both. The fallback `$or: [{owner_id: X}, {cellar_id: X}]` query in `cellar_event_view.py` ensures events are still owner-scoped. However, events without `wine_id` won't appear in wine-detail transaction history and won't be cleaned up when a wine is deleted.
- **Recommendation:** Add `owner_id=current_user.id` and extract `wine_id` from the cellar item's embedded wine in both endpoints.
- **Status:** Carried forward from 2026-08-04 review.

**INFO-53: CSP header missing on nginx-served landing page**

- **File:** `deploy/nginx-winebox.conf`
- **Detail:** The landing page at `winebox.app` is served directly by nginx (static HTML) and does not include the CSP header that the FastAPI application adds via `SecurityHeadersMiddleware`. The landing page contains no dynamic content, user input, or JavaScript beyond static analytics.
- **Recommendation:** Add CSP headers at the nginx level for the landing page server block.
- **Status:** Carried forward from 2026-08-04 review.

**INFO-54: Deprecated `datetime.utcnow()` usage in migration script and test**

- **Files:** `scripts/rename_mongodb_database.py`, test files
- **Detail:** Uses `datetime.utcnow()` (timezone-naive) instead of `datetime.now(timezone.utc)` (timezone-aware). These are in migration/test utility code, not in the main application. The main application correctly uses `datetime.now(timezone.utc)` throughout.
- **Status:** Carried forward from 2026-08-04 review.

**INFO-55: Wine.inventory.quantity not decremented by case/bottle event endpoints**

- **Files:** `winebox/routers/cases.py`, `winebox/routers/bottles.py`
- **Detail:** The case and bottle event endpoints create CellarEvent records but do not update `Wine.inventory.quantity`. The canonical path (`bottle_service.py`) handles this. Functional integrity issue affecting cellar summary accuracy — not a security vulnerability.
- **Status:** Carried forward from 2026-08-04 review.

**INFO-56: Unbounded `skip` parameter on most list endpoints**

- **Files:** `winebox/routers/met.py:17`, `winebox/routers/price_tracker.py:307,380`, `winebox/routers/wines/crud.py:23`, `winebox/routers/transactions.py:32`, `winebox/routers/search.py:46`, `winebox/routers/cellar.py:25`
- **Detail:** The `skip` parameter on these endpoints has `ge=0` but no upper-bound constraint (`le=`). A client can pass `skip=999999999`, forcing MongoDB to walk and discard that many documents. Mitigated by owner-scoped queries (small per-user result sets), global rate limiting (60/min), and MongoDB socket timeout (30s). The X-Wines search endpoint correctly uses `le=10000`.
- **Recommendation:** Add `le=MAX_USER_RESULTSET` (10000) to all `skip` parameters.
- **Status:** Added in 2026-08-06 review.

**INFO-57: Unbounded `$in` array in xwines price filter (up to 50,000 IDs)** *(new)*

- **File:** `winebox/routers/xwines.py:132-134`
- **Detail:** `_get_price_filtered_ids()` loads up to 50,000 xwines IDs into a Python set via `.to_list(length=50000)`, which is then passed as `list(allowed_ids)` into a `$in` query. While bounded at 50,000, this is a very large `$in` clause that could degrade MongoDB query performance and consume significant memory. The X-Wines data is a public reference dataset (not user-owned), so the query is inherently unbounded by user scope.
- **Impact:** Performance degradation under broad price filter queries. Not a data exposure or injection risk.
- **Recommendation:** Consider using a two-stage aggregation pipeline or `$lookup` instead of materializing IDs. Alternatively, lower the cap to 10,000 with a user-friendly error for overly broad price ranges.
- **Status:** New finding.

**INFO-58: `WinePrice` document uses growing embedded `prices` array** *(new)*

- **File:** `winebox/models/wine_price.py`
- **Detail:** The `WinePrice` document embeds a `prices: list[PriceEntry]` array that grows over time as users add price observations. The project's CLAUDE.md states "Prefer one document per item over embedded arrays" and "Embedded arrays create 16MB limits, rewrite-on-update costs." For a crowdsourced price tracker, this array could grow indefinitely for popular wines. The existing `WinePriceHistory` archival system partially mitigates this.
- **Impact:** Schema design concern. Could theoretically approach the 16 MB document limit for very popular wines over a long time horizon. Not a direct security vulnerability.
- **Recommendation:** Enforce a maximum array size (keep only the N most recent entries, archiving older ones) or migrate to one-document-per-price-entry.
- **Status:** New finding.
